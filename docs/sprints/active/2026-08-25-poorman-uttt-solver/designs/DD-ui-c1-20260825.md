## 1. Scope and fixed inputs

This design settles the s1 ui domain: a Vite + React + TypeScript web app that opens referee game logs (harness log schema v1) and provides move-by-move replay and chess-engine-style analysis.

Fixed inputs, not design questions:
- R5: no browser bridge, no play-vs-engine, no sealed-bid entry UX in s1. Play arrives later as an additive supplement; this design must not block it but designs nothing for it.
- Harness log schema v1 (DD-harness-c1-20260825 §8) is the sole game-data input, including its sufficiency contract: every displayed frame is reconstructible from the log alone with zero re-execution.
- Analysis data is the logged verbatim `info` object per turn reply (DD-harness-c1-20260825 §4): recommended keys `t`, `critical_bid`, `pv_if_win`, `pv_if_lose`, `quality` (`"exact" | "bound" | "estimate"`); optional, advisory, possibly absent or malformed.
- Theory fixture conventions: `forced` is integer 0–8 or `null`; local boards and cells 0–8 row-major; canonical marks `X`/`O`.
- Layout inspiration only from ultimate-ttt@0c05c6f; no code reuse (both ui-c1 audits, UI-A01).
- All monetary values are integers in fixed-point units (10^9 = starting budget); they and their sums fit IEEE-754 doubles exactly.

## 2. Architecture principle — log-driven, zero re-execution

The UI contains **no rules engine**. Board snapshots (`post_board`), budgets (`budgets_after`), closures, forced-board routing (`forced_next`), auction resolutions, faults, recoveries, and terminals are all read from the log, never recomputed. Consequences:

- A parsed game is one immutable value (`GameRecord`); the replay model is a pure derivation (`ReplayModel`, §2.1); view state is a single small reducer (`{cursor, toggles}`). No Redux, no state library, no router library.
- The UI can never disagree with the referee about rules. If the log is insufficient to render something, that is a harness-schema gap and routes through s1.orchestrator-planner (never patched around locally).
- Hash-fragment deep-linking (`#cursor=12`) for shareable positions; hand-rolled (one effect syncing the reducer with `location.hash`).

## 2.1 Replay timebase — the typed step model (M1)

The timebase is explicit and total. One `ReplayModel` per game:

- **Positions.** `position_k` for `k ∈ [0..R]`, where `R` is the count of RESOLVED auctions. `position_0` comes from `game_start` (empty board, initial budgets, `forced = 4` framing for the pending ply 0, `tie_owner = null`). `position_k` (k ≥ 1) is read verbatim from resolved auction k's `post_board`, `budgets_after`, `forced_next`. The displayed tie owner at `position_k` is the seat opposite the applied mover of auction k (rule 4a stated, not computed rules execution — it is a one-line restatement of the logged `resolution.winner`; `null` at `position_0`).
- **Steps.** A typed sequence: `SetupStep` (game_start facts, per-seat startup `hello_record`s; when the game terminates at setup — `hello_fault`, zero auctions — the terminal attaches HERE and the cursor space is exactly `[0..0]`), then one `AuctionStep_j` per ATTEMPTED auction (j = 1..A, A ≥ R), then `TerminalStep` (game_end facts) wherever the log ends.
- **AuctionStep contents.** `pre = position_{j-1}` (by reference); the attempts array (per attempt: `request_id`, per-seat `turn_record` — bid, intent, `info`, fault class); `recovery` events causally preceding this step's conclusion attach to this step, in logged order; `outcome`: `resolved` (carries `resolution` + defines `position_j`) or `voided` / `aborted_recovery_fault` (position unchanged; the game terminates; no `position_j` exists).
- **State association invariant.** Every seat's bid, intent, `info` analysis, and both conditional ghosts of `AuctionStep_j` belong to `pre = position_{j-1}` — the state the engines were actually asked about — never to `position_j`. Post-state is never inferred by executing rules; it is read from the log or it does not exist.
- **Views consume it as:** cursor `k` means "after k resolved auctions". The board always renders `position_k`. The pending auction is `AuctionStep_{k+1}` (when it exists): its intents, ghosts, and analysis render on `position_k` — the correct pre-auction board. The just-resolved annotation (last-move emphasis, payment, resolution reason) comes from `AuctionStep_k`. Clicking timeline row j sets cursor to `j−1` (that auction pending, its analysis live); stepping forward resolves it to cursor `j` with the reveal animation. Unresolved terminal steps (void/abort) and the terminal banner render at the final cursor without advancing position.
- **Falsifiable tests (named acceptance):** (a) a zero-auction `hello_fault` fixture renders setup + terminal with cursor space `[0..0]` and no board step controls beyond it; (b) a fixture ply where the applied move differs from BOTH conditional ghost destinations must render the ghosts on the pre-auction board (cursor `j−1`) and never on the post-resolution board — proving the overlay's state association.

## 3. Module decomposition (`ui/` monorepo surface)

- `src/log/` — parsing and validation of log schema v1. JSONL split; per-event schema validation (fail-closed on missing/type-invalid required keys; unknown keys ignored per the protocol's forward-compatibility rule); TypeScript types mirroring `game_start`, `auction`, `recovery`, `game_end`, `turn_record`, `hello_record`; `log_version` check (reject non-1 with a versioned error). Errors are structured `LogError {line, event_index, reason}` rendered as a load-failure screen, never a blank page or console-only failure.
- `src/replay/` — pure event fold: `deriveReplayModel(GameRecord): ReplayModel` implementing §2.1 exactly: `SetupStep`, `AuctionStep[]` (attempts, recoveries, outcome), `TerminalStep`, `position_0..R`. Handles every `auction.outcome` and all six `game_end` reasons, including zero-auction setups; the fold is total over the harness conformance fixtures.
- `src/analysis/` — `info` extraction, keyed per seat per `AuctionStep` and bound to that step's PRE-auction position (§2.1): `AnalysisEntry {t, critical_bid, pv_if_win, pv_if_lose, quality, lo, hi, depth, complete} | {unavailable, why}` — the full value-quality metadata shape locked by DD-engine-rules-c1-20260825 §10 @ sha256 265773e3a98adcd7f8e297e9ca9fc394581ba2506bd660e248b000320ea03f47 (M3). Malformed or absent `info` (friend engines omit it) degrades to `unavailable` with the reason surfaced — the UI never invents, interpolates, or silently hides analysis values, and malformed advisory `info` never invalidates an otherwise valid log. Also builds the whole-game T/p series for the chart, with gaps (not interpolation) where analysis is unavailable.
- `src/format/` — the only place money and shares are formatted. Integer units in, strings out: primary percent form (2 decimals), exact-unit form with digit grouping, and share `p = B_X/(B_X+B_O)` computed in floating point for display only (never for equality decisions; exact comparisons happen only on integers, and the only equality the UI ever states — exact tie — is read from the log's resolution reason, not recomputed). Zero-denominator totality (M2): when `B_X + B_O = 0` (theory-required all-in-to-both-zero states), `p`, the signed margin `p−T`, and any percent-of-combined value return a typed `not-applicable — both budgets exhausted` result, rendered as such; exact integer budgets (0 / 0) and any verbatim analysis fields that remain meaningful are still shown. A formatter/metrics test uses the both-zero fixture shape.
- `src/components/` — presentational: `Board` (nested CSS-grid `BigBoard`/`LocalBoard`/`Cell`), `Timeline` (one row per auction, expandable attempts), `MetricsPanel`, `TPChart` (small custom SVG line chart; no chart library), `BudgetBars`, ghost badges, recovery/fault markers, terminal banner.
- `src/app/` — `Home` (file picker + drag-drop for `.jsonl`, localStorage recents with clear-all, one bundled sample game) and `GameView` (board + timeline + collapsible analysis panel + chart).

Dependency policy: production deps are react and react-dom only; everything else is dev tooling. Exact version pinning is PLAN-owned (UI-A08).

## 4. Data flow and error handling

```
File/drop/recent/sample → text → log/parse → GameRecord | LogError
GameRecord → replay/deriveReplayModel → ReplayModel (immutable, derived once)
GameRecord → analysis/extract   → AnalysisEntry[] + TPSeries
{ReplayModel, AnalysisEntry[]} × {cursor, toggles} → components (pure props)
```

- Load errors: structured error screen (line/event/reason), original file retained for re-try; a valid-but-voided game renders with its void terminal explained, not treated as an error.
- Recents: localStorage stores `{name, opened_at, result, log_text}` (logs are tens of KB); quota failures degrade to session-only recents with a notice.
- Truncated logs, reconciled with fail-closed parsing (M5): partial viewing accepts exactly a schema-valid complete-event prefix. The single tolerated defect is a FINAL byte sequence that lacks a terminating newline AND fails JSON parse — that is the crash-truncation signature; it is discarded with a visible "log ends mid-game (truncated final line discarded)" marker. Everything else fails closed as `LogError`: any newline-terminated line that fails JSON parse, any parsed event that fails schema validation, wherever it sits. A complete-prefix log with no `game_end` is viewable with an "ends mid-game" terminal banner. Acceptance cases: (a) complete prefix missing `game_end` → viewable; (b) unterminated malformed final line → viewable prefix + truncation marker; (c) malformed interior line → `LogError`.

## 5. Replay surface

- Timeline: one row per attempted auction — ply, both revealed bids (percent + exact on hover), both intents, resolution reason (`higher_bid`, `tie_last_mover`, `tie_coin` with coin outcome, `fault` with fault class), payment, post-budgets, `forced_next`; expandable sub-rows for R2 re-request attempts with per-seat fault classes and raw-capture presence; recovery markers between rows; hello/void/abort/terminal rows for `game_end` reasons `hello_fault`, `recovery_fault`, `triple_double_fault_void`, `macro_win`, `chip_count`, `exact_tie_draw`.
- Board: renders `position_k` for the current cursor per §2.1 — last-applied move (from `AuctionStep_k`) emphasized; closed boards overlaid with winner/full state; the PENDING auction's forced board outlined; the pending auction's losing side is unknowable pre-reveal, so the grill's losing-intent display (decision 3) renders both seats' intents of the JUST-RESOLVED auction: applied move solid, the loser's unapplied intent as a dimmed ghost with a hide toggle, on the position where it legibly belongs (`position_{k-1}` context, annotated onto `position_k` only when its cell is still empty; otherwise shown in the timeline row alone).
- Navigation: click any row; ←/→ step, Home/End jump, PageUp/PageDown ±5; focus persists across steps; all controls are real buttons with accessible names (folds ui.implementer audit's a11y findings, incl. native `disabled` semantics, UI-A06).

## 6. Analysis surface

- Metrics panel (X-centric throughout — grill decision 1): threshold `T`, actual share `p`, signed margin `p−T` with a plain-language favored label (both subject to the §3 both-zero not-applicable state), critical bid in exact units and — when a combined budget exists — percent-of-combined, and the two conditional lines.
- Value-quality metadata, full shape (M3): the panel consumes and renders the complete contract locked by DD-engine-rules-c1-20260825 §10 — `quality` (`exact`/`bound`/`estimate`), the `[lo, hi]` interval whenever `quality = bound` (rendered in the same dual percent/exact form as `t`, never as a bare badge), and `depth`/`complete` provenance when present. Partial or malformed metadata degrades field-by-field to `unavailable` with the reason; advisory `info` content never invalidates the log.
- Per-seat `info` semantics (M4): each seat's turn reply may carry its own `info`, so a ply can have zero, one, or two analysis objects, each bound to the step's pre-auction position (§2.1). `t` renders X-centric — that frame is pinned by the approved engine owner record. The `pv_if_win`/`pv_if_lose` perspective (emitter-relative vs canonical X/O) and the stable pre-auction state key are NOT yet pinned in the producing owner contracts: closing them is a REQUIRED pre-PLAN input, routed through s1.orchestrator-planner (§9). Until that ruling lands, the UI defines these fields as `unavailable — perspective unpinned` and renders no conditional ghosts from them; no speculative mapping. The seat-mapping function remains the single isolation point so the ruling lands as one change. The panel defaults to the seat that has analysis and offers a seat selector when both do.
- Conditional best moves: both rendered simultaneously as distinct ghost badges on the PENDING auction's pre-auction position only (§2.1) — if-X-wins styled X, if-O-wins styled O, split badge when they coincide; cleared on every step; distinguished by shape + letter + color (never color alone); legend in the panel (grill decision 4, timing clarified: one ply of lookahead, never stacked hypotheticals). Ghost rendering activates only once the M4 perspective ruling lands; the grill decision fixes the presentation, the ruling fixes the mapping.
- T/p chart: whole-game series, current replay-cursor marker, gaps where analysis is unavailable; SVG, follows the dataviz-skill palette/accessibility rules at implementation time.
- Budget display everywhere: percent primary; exact integer units always available on hover and always shown in full at resolution points — payments, tie explanations, critical bid (grill decision 2).
- Absent analysis (friend-engine games): panel and chart show honest "no analysis in this log" states; replay remains fully functional.

## 7. Visual and accessibility direction

Analytical minimalism (grill decision 6): neutral light/dark surfaces, one accent per player, color-blind-safe pairs, data-ink-first, restrained motion (auction-reveal micro-animation only, honoring `prefers-reduced-motion`). Non-color cues for every board state (legal/forced/closed/won/ghost). Keyboard-first; screen-reader names for cells ("local 4, cell 2, X"), timeline rows, and metric readouts.

## 8. Testing and acceptance

- Vitest + React Testing Library; jsdom.
- Golden-fixture tests: every harness conformance fixture log (success transcript, one per fault class, recovery-fault terminals, void) must parse, derive frames, and render a timeline without error — the fault matrix is the UI's E2 backbone.
- Coordinate-convention tests assert the shared row-major 0–8 grammar against theory's fixture conventions (UI-A05) — types and rendering, not rules logic.
- `format/` property tests: percent/unit round-trips, digit grouping, no float equality anywhere (lint rule + test).
- Replay-model derivation unit tests for every `auction.outcome` and `game_end` reason enum member (totality), plus the two §2.1 falsifiable cases: zero-auction `hello_fault` setup-terminal rendering, and pre-auction ghost association where the applied move differs from both ghost destinations.
- M2/M5 acceptance: both-zero-budget formatter/metrics case; complete-prefix-missing-`game_end`, truncated-final-line, and malformed-interior-line loader cases.
- Playwright E2E (open sample → step → inspect analysis) is PLAN-owned scope, not a design commitment.
- Acceptance: a real engine-vs-engine log and every conformance fixture open and replay correctly; analysis panel matches logged `info` verbatim; a log with zero `info` objects is fully usable.

## 9. Boundary contracts

- Consumes: harness log schema v1 (+ JSON Schemas in `docs/protocol/schema/` as the machine-readable source for `src/log/` types and test fixtures); theory coordinate/`forced` conventions; harness conformance fixture logs as test inputs.
- Writes: nothing consumed by any other pair. localStorage is UI-private.
- Target entity: rendered replay/analysis views.
- Downstream consumer: human (operator, players, friend-engine author reading a lost game).
- Contract changes: any log-schema insufficiency discovered during implementation routes through s1.orchestrator-planner as a harness-schema issue; the UI never compensates locally.
- REQUIRED pre-PLAN gate, orchestrator-routed (M4): the producing owner contracts (harness conformance doc / engine owner record) must pin (a) the `pv_if_win`/`pv_if_lose` perspective — emitter-relative vs canonical X/O — and (b) the stable pre-auction state key for analysis association beyond turn-record attachment. `t`'s X-centric frame is already pinned by the approved engine record and is not part of the gate. Until the ruling exists, the UI defines PV fields as unavailable (§6) and this pair's PLAN does not treat the analysis seam as locked. The ruling is cited from the PLAN when it lands.
- No-consumer action: not applicable (human consumers).
- Forward seam (not built now): `GameRecord`/`ReplayModel` are transport-agnostic — a future bridge feeds the same shapes from live events, which is the R5 supplement's natural insertion point.

## 11. Risks

- Log-schema drift before harness IMPL lands: the UI builds against DD-harness-c1's schema and the published JSON Schemas; if harness implementation diverges, the conformance fixtures catch it — the fixtures, not this design, are the tie-breaker, and deltas route through the orchestrator.
- `info` is engine-authored and advisory: adversarially malformed or oversized-but-capped `info` must never crash the panel (structured degrade path in §6 covers it; fixture test named in §8).
- localStorage recents hold full logs: multi-MB tournament logs could hit quota — degrade path in §4; if real logs exceed tens of KB materially, recents store metadata + re-open-by-file instead (implementer's discretion at PLAN/IMPL, no schema impact).
- Sample game staleness: the bundled sample must be regenerated from the real referee once harness ships, and is a named PLAN deliverable, not a hand-authored artifact.
