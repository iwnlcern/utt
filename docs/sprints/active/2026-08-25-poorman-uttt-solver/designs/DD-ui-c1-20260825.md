## 1. Scope and fixed inputs

This design settles the s1 ui domain: a Vite + React + TypeScript web app that opens referee game logs (harness log schema v1) and provides move-by-move replay and chess-engine-style analysis.

Fixed inputs, not design questions:
- R5: no browser bridge, no play-vs-engine, no sealed-bid entry UX in s1. Play arrives later as an additive supplement; this design must not block it but designs nothing for it.
- Harness log schema v1 (DD-harness-c1-20260825 §8) is the sole game-data input, including its sufficiency contract: every displayed frame is reconstructible from the log alone with zero re-execution.
- Analysis data is the logged verbatim `info` object per turn reply (DD-harness-c1-20260825 §4): recommended keys `t`, `critical_bid`, `pv_if_win`, `pv_if_lose`, `quality` (`"exact" | "bound" | "estimate"`); optional, advisory, possibly absent or malformed.
- Theory fixture conventions: `forced` is integer 0–8 or `null`; local boards and cells 0–8 row-major; canonical marks `X`/`O`.
- Layout inspiration only from ultimate-ttt@0c05c6f; no code reuse (both ui-c1 audits, UI-A01).
- All monetary values are integers in fixed-point units (10^9 = starting budget); they and their sums fit IEEE-754 doubles exactly.

## 2. Architecture principle — log-driven, zero re-execution

The UI contains **no rules engine**. Board snapshots (`post_board`), budgets (`budgets_after`), closures, forced-board routing (`forced_next`), auction resolutions, faults, recoveries, and terminals are all read from the log, never recomputed. Consequences:

- A parsed game is one immutable value (`GameRecord`); per-ply display frames are a pure derivation (`Frame[]`); view state is a single small reducer (`{ply, toggles}`). No Redux, no state library, no router library.
- The UI can never disagree with the referee about rules. If the log is insufficient to render something, that is a harness-schema gap and routes through s1.orchestrator-planner (never patched around locally).
- Hash-fragment deep-linking (`#ply=12`) for shareable positions; hand-rolled (one effect syncing the reducer with `location.hash`).

## 3. Module decomposition (`ui/` monorepo surface)

- `src/log/` — parsing and validation of log schema v1. JSONL split; per-event schema validation (fail-closed on missing/type-invalid required keys; unknown keys ignored per the protocol's forward-compatibility rule); TypeScript types mirroring `game_start`, `auction`, `recovery`, `game_end`, `turn_record`, `hello_record`; `log_version` check (reject non-1 with a versioned error). Errors are structured `LogError {line, event_index, reason}` rendered as a load-failure screen, never a blank page or console-only failure.
- `src/replay/` — pure event fold: `deriveFrames(GameRecord): Frame[]`. A `Frame` carries the ply, board (nine 9-char strings), budgets, forced board, tie owner, the full auction record for that ply (all attempts, both seats' `turn_record`s, resolution or void/abort outcome), any recovery events causally preceding it, and terminal info on the last frame. Handles every `auction.outcome` and all six `game_end` reasons; the fold is total over the harness conformance fixtures.
- `src/analysis/` — `info` extraction: per-frame `AnalysisEntry {t, critical_bid, pv_if_win, pv_if_lose, quality} | {unavailable, why}`. Malformed or absent `info` (friend engines omit it) degrades to `unavailable` with the reason surfaced — the UI never invents, interpolates, or silently hides analysis values. `quality` is displayed verbatim (exact/bound/estimate badge). Also builds the whole-game T/p series for the chart, with gaps (not interpolation) where analysis is unavailable.
- `src/format/` — the only place money and shares are formatted. Integer units in, strings out: primary percent form (2 decimals), exact-unit form with digit grouping, and share `p = B_X/(B_X+B_O)` computed in floating point for display only (never for equality decisions; exact comparisons happen only on integers, and the only equality the UI ever states — exact tie — is read from the log's resolution reason, not recomputed).
- `src/components/` — presentational: `Board` (nested CSS-grid `BigBoard`/`LocalBoard`/`Cell`), `Timeline` (one row per auction, expandable attempts), `MetricsPanel`, `TPChart` (small custom SVG line chart; no chart library), `BudgetBars`, ghost badges, recovery/fault markers, terminal banner.
- `src/app/` — `Home` (file picker + drag-drop for `.jsonl`, localStorage recents with clear-all, one bundled sample game) and `GameView` (board + timeline + collapsible analysis panel + chart).

Dependency policy: production deps are react and react-dom only; everything else is dev tooling. Exact version pinning is PLAN-owned (UI-A08).

## 4. Data flow and error handling

```
File/drop/recent/sample → text → log/parse → GameRecord | LogError
GameRecord → replay/deriveFrames → Frame[] (immutable, derived once)
GameRecord → analysis/extract   → AnalysisEntry[] + TPSeries
{Frame[], AnalysisEntry[]} × {ply, toggles} → components (pure props)
```

- Load errors: structured error screen (line/event/reason), original file retained for re-try; a valid-but-voided game renders with its void terminal explained, not treated as an error.
- Recents: localStorage stores `{name, opened_at, result, log_text}` (logs are tens of KB); quota failures degrade to session-only recents with a notice.
- Truncated logs (referee crash mid-game): frames derived up to the last complete event, with a visible "log ends mid-game" marker — partial logs are viewable, not rejected.

## 5. Replay surface

- Timeline: one row per attempted auction — ply, both revealed bids (percent + exact on hover), both intents, resolution reason (`higher_bid`, `tie_last_mover`, `tie_coin` with coin outcome, `fault` with fault class), payment, post-budgets, `forced_next`; expandable sub-rows for R2 re-request attempts with per-seat fault classes and raw-capture presence; recovery markers between rows; hello/void/abort/terminal rows for `game_end` reasons `hello_fault`, `recovery_fault`, `triple_double_fault_void`, `macro_win`, `chip_count`, `exact_tie_draw`.
- Board: moves made through the selected ply; last-applied move emphasized; closed boards overlaid with winner/full state; forced board outlined; losing intent shown by default as a dimmed ghost with a hide toggle (grill decision 3).
- Navigation: click any row; ←/→ step, Home/End jump, PageUp/PageDown ±5; focus persists across steps; all controls are real buttons with accessible names (folds ui.implementer audit's a11y findings, incl. native `disabled` semantics, UI-A06).

## 6. Analysis surface

- Metrics panel (X-centric throughout — grill decision 1): threshold `T`, actual share `p`, signed margin `p−T` with a plain-language favored label, critical bid in both percent-of-combined and exact units, `quality` badge, and the two conditional lines.
- Per-seat `info` semantics: each seat's turn reply may carry its own `info`, so a ply can have zero, one, or two analysis objects. The UI's frame assumptions: `t` is the game-global X-centric threshold (the defined theory quantity); `pv_if_win`/`pv_if_lose` are relative to the emitting seat and are mapped by the UI through that seat's identity to if-X-wins/if-O-wins. The panel defaults to the seat that has analysis (our engine in mixed games) and offers a seat selector when both do. These frame conventions are not yet pinned in the harness conformance doc for harness-owned producers — named below as a pre-PLAN orchestrator-routed clarification; the UI mapping layer isolates whichever ruling lands.
- Conditional best moves: both rendered simultaneously as distinct ghost badges on the current position's pending auction only — X-styled for `pv_if_win`(X), O-styled for the O line, split badge when they coincide; cleared on every step; distinguished by shape + letter + color (never color alone); legend in the panel (grill decision 4, timing clarified: one ply of lookahead, never stacked hypotheticals).
- T/p chart: whole-game series, current ply cursor, gaps where analysis is unavailable; SVG, follows the dataviz-skill palette/accessibility rules at implementation time.
- Budget display everywhere: percent primary; exact integer units always available on hover and always shown in full at resolution points — payments, tie explanations, critical bid (grill decision 2).
- Absent analysis (friend-engine games): panel and chart show honest "no analysis in this log" states; replay remains fully functional.

## 7. Visual and accessibility direction

Analytical minimalism (grill decision 6): neutral light/dark surfaces, one accent per player, color-blind-safe pairs, data-ink-first, restrained motion (auction-reveal micro-animation only, honoring `prefers-reduced-motion`). Non-color cues for every board state (legal/forced/closed/won/ghost). Keyboard-first; screen-reader names for cells ("local 4, cell 2, X"), timeline rows, and metric readouts.

## 8. Testing and acceptance

- Vitest + React Testing Library; jsdom.
- Golden-fixture tests: every harness conformance fixture log (success transcript, one per fault class, recovery-fault terminals, void) must parse, derive frames, and render a timeline without error — the fault matrix is the UI's E2 backbone.
- Coordinate-convention tests assert the shared row-major 0–8 grammar against theory's fixture conventions (UI-A05) — types and rendering, not rules logic.
- `format/` property tests: percent/unit round-trips, digit grouping, no float equality anywhere (lint rule + test).
- Frame-derivation unit tests for every `auction.outcome` and `game_end` reason enum member (totality).
- Playwright E2E (open sample → step → inspect analysis) is PLAN-owned scope, not a design commitment.
- Acceptance: a real engine-vs-engine log and every conformance fixture open and replay correctly; analysis panel matches logged `info` verbatim; a log with zero `info` objects is fully usable.

## 9. Boundary contracts

- Consumes: harness log schema v1 (+ JSON Schemas in `docs/protocol/schema/` as the machine-readable source for `src/log/` types and test fixtures); theory coordinate/`forced` conventions; harness conformance fixture logs as test inputs.
- Writes: nothing consumed by any other pair. localStorage is UI-private.
- Target entity: rendered replay/analysis views.
- Downstream consumer: human (operator, players, friend-engine author reading a lost game).
- Contract changes: any log-schema insufficiency discovered during implementation routes through s1.orchestrator-planner as a harness-schema issue; the UI never compensates locally.
- Pre-PLAN orchestrator-routed clarification (named obligation): the `info` key frame conventions for harness-owned producers — `t` frame (X-centric assumed) and `pv_if_win`/`pv_if_lose` seat-relativity (emitting-seat-relative assumed) — should be pinned in the harness conformance doc; the UI's §6 mapping layer isolates the ruling either way, so this clarifies rather than blocks.
- No-consumer action: not applicable (human consumers).
- Forward seam (not built now): `GameRecord`/`Frame` are transport-agnostic — a future bridge feeds the same shapes from live events, which is the R5 supplement's natural insertion point.

## 11. Risks

- Log-schema drift before harness IMPL lands: the UI builds against DD-harness-c1's schema and the published JSON Schemas; if harness implementation diverges, the conformance fixtures catch it — the fixtures, not this design, are the tie-breaker, and deltas route through the orchestrator.
- `info` is engine-authored and advisory: adversarially malformed or oversized-but-capped `info` must never crash the panel (structured degrade path in §6 covers it; fixture test named in §8).
- localStorage recents hold full logs: multi-MB tournament logs could hit quota — degrade path in §4; if real logs exceed tens of KB materially, recents store metadata + re-open-by-file instead (implementer's discretion at PLAN/IMPL, no schema impact).
- Sample game staleness: the bundled sample must be regenerated from the real referee once harness ships, and is a named PLAN deliverable, not a hand-authored artifact.
