## Finding 1 — "layout inspiration only, NO code reuse" judgment: CONFIRMED (E1)

Audited the reference at /tmp/uttt-ref (github.com/ultimate-ttt/ultimate-ttt @ 0c05c6f, Sat Sep 11 2021; MIT license, LICENSE:1 — so reuse would be legally fine; the bar is technical).

- Obsolete stack: CRA `react-scripts` 3.4.4, React 17, redux 4 + redux-saga 1.1.3 + redux-persist + reselect + rmwc (package.json dependencies block). Incompatible with the spec's Vite + React (19.2.8 current) + TS target; migration cost exceeds rewrite for ~143 src files.
- Alternating-turn state machine is load-bearing and wrong for bidding: `src/state/currentGame/game/gameReducer.ts:16-19` toggles `currentPlayer` Cross↔Circle unconditionally, and `src/state/currentGame/moves/moveValidationSaga.ts:23` fires `yield put(changePlayer())` after every move. Under auction rules the same player can move many times in a row; there is no bid, budget, auction-resolution, tie-owner, or chip-margin concept anywhere in `src/state/AppState.ts`'s game model. The turn machine is woven through sagas (move → changePlayer → calculateActiveBoards → checkGameFinished), so surgery is a rewrite in place.
- Terminal logic differs: their draw is a plain draw; our rules decide drawn games by chip comparison (design spec rule 8). Their `checkGameFinishedSaga` has no budget input.

Worth borrowing as ideas (E1, file:line):
- Nested CSS-grid board: `BigBoard.module.css:1-6` (`grid-template-columns: repeat(3, 1fr)`) containing 9 SmallBoards, each a 3×3 of Tiles; active-board affordance via `activeBoards: Point[]` + `moveAllowed` prop (`BigBoard.tsx:40-45, 69`), won-board overlay via `boardIsFinished` (`SmallBoard.tsx:51-58`).
- Analysis screen composition: `grid-template-areas` moveList / historyButtons / game with responsive re-flow (`AnalysisGame.module.css:1-18`); move list scroll-synced to current move with keyboard-driven ArrowButtons (`AnalysisGameDisplay.tsx:16-24, 44-55`).
- Highlight plumbing for last-move/hint marking (`BigBoard.tsx:26-38`).
Bidding adaptations our layout needs that theirs cannot express: per-move bid pair + budgets column in the move list, budget bars/clock chrome around the board, and a sealed-bid entry panel.

## Finding 2 — UI needs from the two boundary contracts (E1, for harness before protocol lock)

From the play protocol (design spec :88-91, harness-owned):
1. Analysis-data channel — the spec'd response `{"bid": int, "move": [b, c]}` carries none of the analysis view's required data (threshold T, share p, budget margin, critical bid, if-X-wins/if-O-wins best moves — spec :104). UI needs a decision before lock: (a) optional engine analysis fields in the reply, (b) a separate analysis request type, or (c) referee-side enrichment into the game log. UI is agnostic between them but needs one to exist.
2. Bridge transport — engines speak JSONL over stdin/stdout (spec :88); a browser cannot. UI needs the referee's "local bridge" (spec :103) to expose WebSocket or HTTP+SSE, including: create game, submit human sealed bid+move, receive auction resolution/reveal events, receive clock state. Whether the bridge is in-protocol or a referee sidecar is harness's call; UI needs the message shapes versioned with the protocol.
3. Human-vs-engine sealing semantics — the referee must accept the human's bid without revealing the engine's committed bid (ordering/commitment guarantee visible in the bridge API), and must reveal both bids + tie resolution (incl. first-move coin flip outcome) after resolution.
4. Error/timeout surface — what the UI sees when an engine crashes, misformats, or exceeds 30 s (spec :96 says referee enforces limits; UI needs the forfeit/retry event shape).

From the game-log schema (referee-emitted "replayable JSON game log", spec :96):
5. Per-move record sufficient to reconstruct every UI frame without a rules engine round-trip: move number, both revealed bids, auction winner + resolution reason (higher-bid | tie-alternation | tie-coinflip), mover, cell `[local, cell]`, post-move budgets (fixed-point units), forced-board index or ANY, local-board closure events, macro state.
6. Game-level record: initial budgets, first-move coin-flip outcome, seat/engine identities + versions, per-move time consumed, terminal result with reason (macro-win | chip-lead | exact-tie ½–½) and final budgets.
7. Optional per-move analysis block (T, p, margin, critical bid, conditional PVs) — same decision as need 1; if analysis rides the log, replay and analysis views merge cleanly.
8. Version field on the log schema, and log values in the same fixed-point integer units as the protocol (spec rule 2, :20-22) so the UI never does float re-derivation of exact ties.

From rules fixtures (theory-owned): machine-readable positions with expected legal moves/closures/outcomes (spec :68-69) — UI will consume them to test its board-rendering and legal-move affordances. Need: a stable JSON shape and repo path; no extra fields beyond what theory already plans.

## Finding 3 — UI surfaces implied by the spec (E1, spec :100-105)

1. Play vs engine: board + budget bars, sealed bid entry (numeric input; slider alone cannot express 10^9 units exactly), intended-move selection, commit → reveal → resolution cycle, forced-board affordance, 30 s clock, terminal screen incl. chip-comparison outcomes.
2. Replay: load game log, step/scrub move list (bid pair + budgets per row), keyboard nav, auction-reveal animation per step.
3. Analysis: threshold T vs share p (with margin), critical bid, both conditional best moves rendered as ghost marks, per-move chart of T/p over the game — chess-engine style (spec :104).
4. Shared: game-log fixture loader for dev (roadmap: "develops against logged fixtures"), protocol/bridge client, rules-display helpers (closure, forced board).
