## 2. Feasibility vs 30 s/move (assessment; E1 = spec/file refs, E0 = my reasoning or unfetched URL)

Feasible with headroom, with one structural caveat about search cutoffs.

- Bitboard plan sound: 9×9-bit locals per player = 81 bits/player → one `__uint128_t` or 2×`uint64` each; 3^9 = 19683-entry per-local tables are KBs and cache-resident — E1 arithmetic vs design spec (Component 2) + E2 uint128 probe above.
- Node budget: prior-art UTTT bitboard engines report microsecond-scale optimized searches and >10^7 nodes/s single-thread; forced-board nodes branch ≤9; 30 s on an M5 Pro gives ~10^8–10^9 node budgets. Depth will be limited by free-choice nodes, not raw speed — E0, corroborated by minimax.dev write-up (URL in §5, content not deep-verified).
- Free-choice branching: worst case ~70+ legal cells, and per the threshold backup EVERY node evaluates both an X-child and an O-child per legal cell (a = min over X moves, b = max over O moves), so effective branching is ~2× legal moves. Selective widening is the right mitigation; it must be in the search design from day one, not retrofitted — E1 vs design spec "Threshold theory" + E0 reasoning.
- CAVEAT (flag, believed underspecified): classic alpha-beta does not transfer. `T = b/(1-a+b)` is monotone increasing in both a and b, so bound propagation works (a lower bound on a and upper bound on b bound T), but the cutoff conditions differ from negamax windows. The design lists "interval branch-and-bound" as a LATER optimization; my assessment is interval/bound propagation is likely CORE to getting any useful pruning at all, and the DESIGN phase should treat cutoff math as a first-class deliverable of the search-math lock (theory-gated). Without it, search is closer to plain minimax-width and depth may disappoint — E0 reasoning against spec lines (backup operator definition).
- TT key (cells + forced-or-ANY + one tie-owner bit): consistent with the spec's claim that T is budget-independent; that claim itself is exactly what theory's gate must confirm, so the TT design must not lock before theory reports — E1 spec "Threshold theory" §. Note the forced-board field is NOT derivable from cells alone (last mover's cell may point at a closed board → ANY), so it belongs in the key as specified; tie-owner is derivable from last-mover identity, so key can carry last-mover instead — equivalent one bit plus a null start state — E0 reasoning.
- First-move coin flip: at the root of move 1 the tie owner is decided by a referee coin flip AFTER bids are sealed, so tie ownership is unknowable at bid time; T(s,h) assumes h known. Root bidding on move 1 needs an expected-value or worst-case rule. This belongs in theory's math lock and in the harness protocol semantics (`last_mover: null`) — flagged, not reinterpreted — E1 vs design spec canonical rule 4b + protocol example.
- Knife-edge p = T under integer bids: bid rounding direction is undefined until theory rules on exact-equality behavior; engine must not pick silently — E1 spec "Open math questions".
- 27 s soft clock + iterative deepening: standard, fine; TT entries need bound-type (exact/lower/upper on T) semantics for ID reuse — E0.

## 3. Open representation questions for DESIGN

1. Position layout: per-player `__uint128_t` vs 9×`uint16` array; cached macro summary (per-player won-mask + closed-mask over the 9 locals).
2. Move encoding: (local 0-8, cell 0-8) in 7 bits; fixed-capacity move lists (≤81), no heap in the hot path.
3. Forced/tie encoding: forced ∈ {0..8, ANY}; store last-mover {X, O, none} (none = pre-coin-flip) rather than a bare tie bit.
4. Threshold value type: double vs fixed-point vs interval [lo, hi]; determinism requirements (engine-vs-exact-solver equality acceptance test needs a defined tolerance) and TT storage width.
5. TT entry layout: 64-bit Zobrist over (81 cells × 2 players, 10 forced states, 3 last-mover states); value + bound type + depth + best move; replacement policy; single-threaded first, sharding deferred.
6. Budget plumbing: budgets (int64 fixed-point units) stay OUTSIDE Position per spec; define the API seam — search maps (Position, tie-state) → T; root layer combines T with budgets for the bid.
7. Protocol I/O boundary: JSONL adapter as a separate translation unit with no core dependency on a JSON lib in the search path; "you/opp" → X/O mapping and `last_mover` → tie-state derivation live in the adapter; consumes the harness-owned schema as-is.
8. Evaluator interface: feature vector → H(s) → sigmoid → T-estimate; weight-fitting is offline (likely Python, cross-pair touchpoint with theory's data) — the C++ side needs only a weights-blob loader.
9. Root bid-matrix + regret-matching module: separate from tree search; consumes root T values and real budgets.
10. Fixture ingestion: theory-owned rules fixtures consumed by C++ tests — the fixture file contract is needed EARLY (before rules-core tests exist); request theory publish format first.
