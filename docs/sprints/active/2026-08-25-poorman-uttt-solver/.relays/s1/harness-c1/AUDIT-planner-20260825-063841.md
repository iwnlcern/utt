## Protocol design questions DESIGN must settle

Audited against the spec sketch (design spec, Component 3, lines 85–98). Each is unstated or ambiguous in the sketch:

1. Framing: UTF-8, one JSON object per LF-terminated line, no embedded newlines, flush after every write (the classic third-party failure mode — must be a normative MUST), unknown-field tolerance for forward compatibility, max line length.
2. Handshake/version: sketch has per-request `"protocol": 1` only. Decide whether v1 adds a one-line hello (engine name/version/author for logs and tournament tables) or stays pure stateless spawn-then-request. Afternoon bar favors minimal.
3. Process lifecycle: persistent process per game (required in practice — engine transposition-table warmth across moves is a strength assumption in the engine design) vs per-request spawn; clean shutdown (message vs SIGTERM vs EOF); crash/EOF mid-game handling; cutechess `-recover` analog for long tournaments.
4. Seat/perspective: the sketch keys budgets `you`/`opp` but never says which board marks are the engine's. Need explicit mark assignment (e.g. `"you": "x"`) or perspective-normalized cells. `last_mover` domain (`"you"`/`"opp"`/null) and, ideally, an explicit tie-owner field so engines don't re-derive rule 4 and diverge off-by-one.
5. Tie/coin-flip mechanics on the wire: who learns the coin-flip result and when; determinism — seeded referee RNG with the seed recorded in the game-log header so tournaments and replays are reproducible (referee owns all randomness).
6. Time control: `time_ms` = fixed per-move 30 000 (spec constraint is per-move) — state when the clock starts/stops (referee write → reply read), referee-side wall-clock enforcement with an explicit grace margin, and whether move 1 gets a warmup allowance (CodinGame precedent).
7. Fault semantics (operator-judgment item below): timeout, malformed JSON, illegal move, illegal bid (negative, non-integer, > budget), missing field. Recommendation: any fault = immediate game loss with logged reason — sealed-bid integrity means no retry can be offered after the opponent's bid is committed.
8. Move-mandatory rule: reply must always carry `move` (used only if the auction is won). Sub-question: is an illegal move from the auction *loser* a fault or ignored? Recommend: fault (deters garbage), but decide explicitly.
9. Bid domain: integers 0..own-budget inclusive; all-in legal; 10^9 units fits IEEE double exactly (< 2^53) so JSON numbers are safe in every language — state this in the spec.
10. Legal-action enumeration: whether requests include the legal cell list (CodinGame lesson; big afternoon-bar win, costs verbosity). Recommend yes.
11. Forced-board encoding: integer 0–8 vs null/"any"; move-1 forced-center representation (`"forced": 4` from the start?).
12. Game-end notification to engines (result + reason) — cheap, helps bot authors; socialgorithm precedent.
13. Diagnostics: engine stderr is free-form and referee-ignored (normative), so debug output can't corrupt the protocol stream; optionally a reserved `info` field for engine analysis (threshold estimate, PV) that flows into the game log — this is the natural carrier for the ui pair's analysis view and should be settled with ui at the boundary.
14. Game-log schema (versioned, harness-owned): header (players+versions, seed, protocol version, time control), per-turn record (both sealed bids revealed post-hoc, auction winner, tie resolution incl. flips, move, budgets after, per-engine elapsed ms), final result (macro-win / chip-count 1–0 / ½–½ / fault-forfeit + reason). Must be sufficient for UI replay with no referee re-execution.
15. Spec-doc versioning/change control: lives in `docs/protocol/`, versioned; all changes route through s1.orchestrator-planner (ROADMAP gates 2–3).

## Afternoon-implementability audit of the sketch

The sketch's shape is right and is the single best decision already made: stateless full-state-per-request JSONL means a third party writes a read-line/parse/reply loop with zero game-state tracking (UCI's full-position precedent; socialgorithm's delta protocol is the counterexample). Gaps that would break an afternoon port today: unstated flush requirement, unspecified mark/seat perspective, undefined fault semantics, imprecise framing. With items 1, 4, 7, 9 settled, plus a reference bot (a baseline bot doubling as executable documentation, ~100 lines of stdlib Python) and a conformance fixture set, the bar is met — E1 (spec lines 88–94 vs the convention pool above).
