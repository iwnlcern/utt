## 2. Canonical state (normative for both pairs; implements ruling R-s2-1)

### 2.1 State identity

A state is exactly:

- `x[9]`: nine 16-bit X occupancy masks, one per local board, bits 0..8 used, bits 9..15 zero.
- `o[9]`: nine 16-bit O occupancy masks, same layout.
- `forced`: one byte, `0..8` = the local board the side to move must play in, `9` = ANY (free choice among open boards).

Side to move is derived, never stored: X moves iff `popcount(all x) == popcount(all o)`; O moves iff X's count exceeds O's by exactly one.
Any other count relationship makes the state ill-formed.
Auction-era TieState and budgets are excluded from s2 state identity (R-s2-1).

Cell and board numbering is row-major, matching `theory/fixtures/SCHEMA.md`:

```text
0 1 2
3 4 5
6 7 8
```

Bit `c` of a local mask is cell `c` of that local board.
A global move is `m ∈ 0..80` with board `m / 9` and cell `m % 9`.

### 2.2 Serialization (37 bytes)

```text
bytes  0..17 : x[0..8], each uint16 little-endian
bytes 18..35 : o[0..8], each uint16 little-endian
byte     36  : forced (0..8, or 9 = ANY)
```

This 37-byte string is the node identity everywhere in the certificate.
There is no hash-as-identity anywhere in the format; hashes are integrity-only (§6).

### 2.3 D4 transforms

The eight symmetries of the square act simultaneously on the macro grid and on every local grid.
A transform `g` maps global cell `(B, c)` to `(g(B), g(c))` using the same index permutation for both levels.
The eight permutations, written as destination tables `dest[i] = g(i)`:

```text
e        : 0 1 2 3 4 5 6 7 8
r90 (cw) : 2 5 8 1 4 7 0 3 6
r180     : 8 7 6 5 4 3 2 1 0
r270 (cw): 6 3 0 7 4 1 8 5 2
mh  (c→2−c, mirror across vertical axis)   : 2 1 0 5 4 3 8 7 6
mv  (r→2−r, mirror across horizontal axis) : 6 7 8 3 4 5 0 1 2
md  (transpose, (r,c)→(c,r))               : 0 3 6 1 4 7 2 5 8
ma  (anti-transpose, (r,c)→(2−c,2−r))      : 8 5 2 7 4 1 6 3 0
```

Applying `g` to a state: new local board `g(b)` receives the mask of old board `b` with its bits permuted by `g` (`new_mask[g(b)] bit g(c) = old_mask[b] bit c`); `forced` maps to `g(forced)` when `forced ≤ 8` and stays `9` when ANY.
Side to move is invariant under all eight transforms (mark counts are preserved).
Color swap (X↔O) is NOT part of identity: it maps a position to a value-negated one, and including it would thread negation semantics through the whole checker (grill decision G2).
The solver may exploit color symmetry privately in its own tables; certificate states never do.

### 2.4 Canonical form

`canon(s)` = the lexicographically smallest of the eight 37-byte serializations of `g(s)` for `g` in D4, compared as unsigned bytes.
Symmetric positions collapse automatically (equal byte strings).
Every state stored in a certificate MUST already be canonical; the checker re-canonicalizes every record and rejects on mismatch.
The convention has the identifier SYMMETRY_ID `d4-lexmin-v1`, carried in every certificate header.

### 2.5 Moves in canonical frame

A stored move is a cell index `0..80` in the coordinate frame of the (canonical) state it is attached to.
The checker computes a child as `canon(apply(state, move))` under the Appendix A rules.
Edges carry no transform annotations; child lookup is by canonical identity.

### 2.6 Well-formedness (checker MUST enforce per record)

- Mask bits 9..15 zero in all 18 masks; `x[b] & o[b] == 0` for every board.
- Mark-count parity: `0 ≤ popcount(x) − popcount(o) ≤ 1`.
- `forced ∈ 0..9`; if `forced ≤ 8`, board `forced` is open (not closed under Appendix A closure).
- The 37 bytes equal their own canonicalization.
- The record's node kind is consistent with the derived side to move and with the certificate claim (§3).

Full reachability from the root is NOT checked per node and does not need to be: the soundness argument (§3.4) flows from the root downward, so junk records that verify locally but are unreachable from the root waste bytes without weakening the proof.
The checker counts and reports orphans (records never referenced during the root's downward closure accounting); a strict mode MAY reject orphans, the default reports them.

## 3. Proof semantics (dual boolean; grill decision G1)

### 3.1 Claims

A certificate proves exactly one claim, named in its header:

```text
WIN_X     — X forces a macro win.
WIN_O     — O forces a macro win.
NOLOSS_X  — X forces macro-win-X or the all-closed draw (X does not lose).
NOLOSS_O  — O forces macro-win-O or the all-closed draw (O does not lose).
```

The prover of a claim is the player named in it.
The game value is assembled by the verdict manifest (§7), never inside one certificate:
X-win ⟺ one WIN_X certificate; draw ⟺ one NOLOSS_X and one NOLOSS_O certificate; O-win ⟺ one WIN_O certificate.
"X has a drawing move" can therefore never masquerade as "X has no winning move": the former lives in NOLOSS_X, the latter is exactly NOLOSS_O, a separate artifact with its own full proof.

### 3.2 Node kinds and node rule

Every node is one of four kinds.
For a certificate with prover P:

- `PROVER` (P to move, state non-terminal): the record declares exactly one move; the move must be legal in the state; the canonical child must be a verified node of this certificate.
- `OPPONENT` (opponent to move, state non-terminal): the record declares nothing; the checker enumerates every legal move of the state and requires every canonical child to be a verified node of this certificate.
- `TERMINAL` (state terminal under Appendix A): the checker recomputes the terminal result and requires it to satisfy the claim — for WIN_P: macro win by P; for NOLOSS_P: macro win by P or the all-closed draw.
- `RULE` (rule-closed leaf): §5.

A terminal state MUST be a TERMINAL record; a non-terminal state MUST NOT be.
Node kind is stored explicitly and cross-checked against derived side-to-move and terminality; any inconsistency rejects.
Terminal labels, values, and any solver opinion are never trusted; the checker recomputes everything from the 37 bytes plus Appendix A.

### 3.3 Root

A certificate's root is the canonical, well-formed state declared in its header; the proof establishes the claim for that state, and the root must end up verified.
The requirement that the deliverable's root be the canonical INITIAL position (all 18 masks zero, `forced = 4`, X to move — the all-zero state is D4-symmetric, hence its own canonical form) lives at the verdict layer (§7), not here.
This is deliberate: §9's hand-authored test certificates and Appendix B's golden vector are rooted at small non-initial states and must be valid certificates.

### 3.4 Soundness argument (informative)

By induction over the leveled DAG from the deepest verified records upward: a TERMINAL record satisfies the claim by recomputation; a PROVER record supplies a legal strategy move into a claim-satisfying position; an OPPONENT record shows every legal reply lands in a claim-satisfying position; a RULE record satisfies the claim by the rule's soundness theorem applied to its validated witness.
The verified root therefore carries the claim for the real game.
Nothing in the argument uses digests, record order beyond child-before-parent availability, or any solver-provided value.

## 4. Container format

SCHEMA_ID: `uttt-cert` SCHEMA_VERSION: `0.1`.
Versioning policy: minor bumps are additive (new rule ids in the registry, new sidecar fields); major bumps may break layout.
A checker accepts only versions on its explicit support list and refuses anything else (fail closed).

### 4.1 Layout

A certificate is a header plus a sequence of chunks.
The game DAG is leveled: every move adds one mark, so node ply = total mark count, and all edges go ply `p` → `p+1`.
Chunks are grouped by ply and ordered by strictly descending ply; within a ply, multiple chunks are allowed (size-capped by the emitter) and records may appear in any order.
This makes record order child-before-parent by construction, and the rank check is local: a child of a ply-`p` node must sit at ply `p+1`, i.e. have exactly one more mark.

### 4.2 Records

Fixed-width record (kinds PROVER, OPPONENT, TERMINAL), 40 bytes:

```text
bytes  0..36 : canonical state (§2.2)
byte     37  : kind (0 = PROVER, 1 = OPPONENT, 2 = TERMINAL, 3 = RULE-in-variable-section)
byte     38  : payload — PROVER: declared move 0..80; others: 0xFF
byte     39  : reserved, must be 0x00
```

RULE records are variable-width and live in a per-ply variable section after the fixed records of that ply (§5.2).
Duplicate canonical states anywhere in one certificate reject (one node, one record).

### 4.3 Certificate wire format (normative byte packing)

A certificate is one file, parsed strictly sequentially: header, manifest rows, manifest digest, then chunks.
All encoding primitives are defined in §4.5.

Header (sequential fields, no padding beyond what is shown):

```text
magic            : 8 bytes ASCII "UTTTCERT"
schema_major     : u16 = 0
schema_minor     : u16 = 1
claim            : u8 — 0 WIN_X, 1 WIN_O, 2 NOLOSS_X, 3 NOLOSS_O
reserved         : 3 bytes, each 0x00
ruleset_id       : str16 = "uttt-s2-r1"
ruleset_digest   : digest16 (§1)
symmetry_id      : str16 = "d4-lexmin-v1"
root_state       : 37 bytes (§2.2, canonical, well-formed)
rule_count       : u16 — number of rule_ids_used entries; MUST be 0 in v0
rule_ids_used    : rule_count × (str16 rule_id, u16 rule_version)
totals           : 4 × u64 — node counts in order PROVER, OPPONENT, TERMINAL, RULE
manifest_rows    : u32 — row count, ≥ 1
```

Manifest row (fixed 40 bytes each, `manifest_rows` of them):

```text
ply              : u8 (0..80) — mark count of every record in the chunk
flags            : u8 = 0x00
ordinal          : u16 — chunk ordinal within its ply, ascending from 0
record_count     : u32 — total records in the chunk (fixed + rule)
byte_offset      : u64 — absolute offset of the chunk from the start of the file
byte_length      : u64 — chunk length in bytes
chunk_digest     : digest16 over exactly the chunk's byte_length bytes at byte_offset
```

After the rows: `manifest_digest` — digest16 over the concatenated manifest-row bytes exactly as stored (rows only, nothing else).
The bytes from offset 0 through the end of `manifest_digest` are the HEADER REGION; the certificate's `header_digest` (used by the verdict manifest, §7) is digest16 over the header region.

Chunk envelope (at each manifest row's offset):

```text
fixed_count      : u32 — number of 40-byte fixed records
rule_count       : u32 — number of RULE records
fixed records    : fixed_count × 40 bytes (§4.2)
rule records     : rule_count × variable (§5.2)
```

Framing and order constraints (each violation rejects):

- Manifest rows sorted by strictly descending `ply`, then ascending `ordinal` starting at 0 per ply with no gaps.
- The first chunk begins immediately after the header region; each subsequent chunk begins immediately where the previous ends (`byte_offset` strictly increasing, no gaps, no overlaps); the file ends exactly at the last chunk's end — trailing bytes reject.
- `record_count == fixed_count + rule_count` per chunk; summed per-kind record counts across the certificate must equal `totals`.
- Every record's mark count must equal its chunk's `ply`.
- The certificate is fully materialized (grill decision G4): every node the checker needs is present in the chunks; verification never invokes any solver or regenerator.

### 4.5 Encoding primitives (normative)

- All integers (`u8`, `u16`, `u32`, `u64`) are unsigned little-endian.
- `str16` = u16 length followed by that many bytes; contents MUST be printable ASCII (0x21–0x7E), length 1..64.
  Verdict member paths (§7) are the one exception: UTF-8, length 1..4096, POSIX `/` separators, relative, no `.` or `..` segments.
- `digest16` = the 16-byte canonical representation of XXH3-128 with seed 0, as defined by the xxHash specification (`XXH128_canonicalFromHash`: big-endian, high 64 bits first).
  This is the byte form `xxhsum -H2` prints as hex.
  Reference anchor: XXH3-128(seed 0) of the empty input is `99aa06d3014798d86001c324468d497f`.
- Unknown, extra, or trailing fields are forbidden at every framing level: a v0 parser rejects any byte it cannot attribute (fail closed); forward compatibility comes from version bumps, never from ignored bytes.

### 4.6 Integrity role of digests (grill decisions G5, G6)

All digests are XXH3-128 and are integrity/ops surfaces only: transport-corruption detection, resume bookkeeping, and manifest binding.
Soundness never rests on a digest — the checker semantically re-verifies every record, so an artifact that passes semantic verification is a valid proof regardless of digest provenance.
Resume after interruption trusts only the checker's own local journal (its recorded per-chunk verdicts and digests), never the artifact's self-declarations.

## 5. Rule-closed leaves and the rule-language versioning hook

### 5.1 Hook contract

A RULE leaf closes a subtree by citing a strategy rule instead of expanding children.

```text
rule_id       : registered ASCII identifier
rule_version  : integer
witness       : length-prefixed blob, layout owned by the rule's own spec
```

Trust base of a RULE leaf, explicitly: the rule's machine-checked soundness theorem (a theory-c4+ artifact, orchestrator-routed) plus the checker's witness validator for that rule/version.
Verification obligation: the checker validates the witness against the rule's published precondition and claim using only its own rules implementation; validation must be a finite, search-free check.
Heuristic evaluations, proof numbers, transposition hits, and search cutoffs are never valid leaf reasons.

The v0 checker ships an EMPTY rule registry: every RULE record fails closed, and a header whose `rule_ids_used` is non-empty is refused outright by a v0 checker.
Registering a rule requires: the soundness artifact, the checker-side validator, a schema minor-version bump, and orchestrator routing (ROADMAP gate 1); certificates list every rule id they use in the header so refusal happens before streaming.

### 5.2 Encoding

RULE records sit in a per-ply variable section: `37-byte state | 0x03 | str16 rule_id | u16 rule_version | u32 witness_len | witness bytes`, using the §4.5 primitives (all integers little-endian; rule_id printable ASCII, 1..64 bytes).
A RULE record participates in the verified set exactly like any other verified node once its witness validates.

## 6. Verification algorithm (normative behavior, not implementation)

1. Parse and validate the header region; refuse on: bad magic; unsupported schema version; unknown claim tag; nonzero reserved bytes; unknown ruleset id or ruleset digest mismatch; unknown symmetry id; ill-formed or non-canonical root_state; `rule_count ≠ 0` (v0); `manifest_rows = 0`; manifest row order/offset/overlap/gap violations (§4.3); manifest digest mismatch.
2. Stream chunks in manifest order (descending ply); per chunk, verify byte length and XXH3-128 digest, then verify records.
3. Per record: well-formedness (§2.6), kind consistency, then the §3.2 node rule; child lookups hit a disk-backed verified-set keyed by the 37 canonical bytes; insert the record into the verified set on success.
4. Reject (fail closed, first failure wins, position reported) on: duplicate state; non-canonical state; ill-formed state; record mark count not equal to its chunk's declared ply; nonzero record reserved byte; non-PROVER fixed record with payload ≠ 0xFF; illegal declared move; missing or unverified child; terminal/kind mismatch; terminal not satisfying the claim; unknown rule id/version; malformed witness; chunk digest or length mismatch; `record_count ≠ fixed_count + rule_count`; streamed per-kind counts ≠ header totals; trailing or truncated bytes; root absent at end.
5. On success emit a machine-readable report: verdict, claim, root state (hex) and whether it is the canonical initial position (`root_is_initial`), ruleset/schema ids and digests, totals, orphan count, checker version, C3 compiler version, wall/CPU time.
   Exit code 0 iff the certificate verifies.

Verdict-manifest mode (§7) runs this per member certificate, then checks the completeness rule.

## 7. Verdict manifest (grill decision G7)

A tiny top-level file is the deliverable's root artifact.
Wire format (sequential, §4.5 primitives, trailing bytes forbidden):

```text
magic            : 8 bytes ASCII "UTTTVRDT"
schema_major     : u16 = 0
schema_minor     : u16 = 1
game_value       : u8 — 0 X-win, 1 draw, 2 O-win
reserved         : 3 bytes, each 0x00
ruleset_id       : str16
ruleset_digest   : digest16
symmetry_id      : str16
root_state       : 37 bytes — the position the value claim is about
member_count     : u8
members          : member_count × (claim u8, path [§4.5 path rules], header_digest digest16)
```

The member `claim` byte uses exactly the §4.3 certificate claim-tag enum (0 WIN_X, 1 WIN_O, 2 NOLOSS_X, 3 NOLOSS_O); any other value rejects.

Verification of a verdict manifest, in order, each failure rejecting:

1. Parse fail-closed (same header refusal style as §6 step 1; unknown game_value or member claim tag rejects).
2. Resolve each member path relative to the manifest's directory; an absent or unreadable target rejects.
3. Verify each member certificate fully (§6).
4. Require each member's `header_digest` to equal digest16 over the referenced certificate's header region.
5. CLAIM BINDING (soundness, not integrity): require `member.claim == referenced certificate header.claim`; a mismatch rejects even when the certificate itself is valid and the digest matches.
6. Require each member certificate's schema version, ruleset id + digest, symmetry id, and root_state to equal the manifest's.
7. Completeness, stated as an exact multiset of member claims (after step 5 these are certified, not declared): game_value X-win → members' claims are exactly {WIN_X}; draw → exactly {NOLOSS_X, NOLOSS_O}; O-win → exactly {WIN_O}.
   Any extra, missing, or duplicate claim rejects.

Verdict verification runs in one of two normative modes:

- `deliverable` (the default): after steps 1–7, VERIFICATION FAILS unless the common root_state is the canonical initial position (§3.3).
  Exit code 0 in this mode is the machine statement of the ROADMAP deliverable — the initial game's value, verified end to end.
- `subgame` (explicitly requested): steps 1–7 only; arbitrary canonical roots accepted; the report still carries `root_is_initial`.
  Format vectors and subgame studies (Appendix B) verify in this mode; a `subgame` pass is never the sprint deliverable.

Per grill decision G3, partial certificates (e.g. NOLOSS_X alone) are internal evidence only, never a shipped deliverable: the sprint deliverable is a `deliverable`-mode verdict pass.

## 8. Independence boundary (implements rulings R-s2-2, R-s2-3; grill decision G8)

- Checker language: C3 (c3-lang.org), newest stable release, pinned in the checker README and echoed in every verification report; idiomatic C3 style, not a defensive C subset (operator direction).
- Throughput justification against the audit's 1e6–1e12 node bracket: native-compiled fixed 40-byte records; per-node cost is legality enumeration plus verified-set probes (microsecond order), so 1e9 nodes is hours on one machine and 1e12 is days shard-parallel by ply/chunk; XXH3 hashing runs above disk bandwidth and is never the bottleneck.
  The binding constraint is disk I/O and verified-set locality, not language speed.
- Fresh implementation of everything semantic: parser, canonical encoder, D4 transforms, legality, transition, closure, terminal evaluation, witness validators.
  No linking to, code generation from, or translation of `engine/src/core` or any solver code (R-s2-2).
- Shared artifacts, exhaustively: this design doc; theory fixtures (v1 frozen per R-s2-4, plus the additive s2 profile in §9).
  `referee/poorman_referee/rules.py` may serve as a third cross-check only, never linked or copied (R-s2-3).
- C3 risk register: young toolchain in the trust base.
  Mitigations: pinned compiler version in every report; the named-mutant suite (§9) exercising every fail-closed path; hand-authored small-certificate cross-checks derived from fixtures; fixtures as shared conformance truth.

### Appendix A — Normative rules of the s2 target game (RULESET_ID uttt-s2-r1)

1. The board is a 3×3 macro grid of 3×3 local boards.
   Players X and O alternate marks; X moves first.
2. The first move of the game must be played in the center local board (board 4); any of its nine cells is legal.
3. A local board is closed when it is won (three in a row of one player's marks within it) or completely full.
   Cells of a closed board are dead: no mark may ever be placed there.
4. A mark in cell c of any local board sends the opponent to local board c: their next mark must be placed in board c, unless board c is closed, in which case their next mark may be placed in any empty cell of any open board.
5. A player who completes three local-board WINS in a row on the macro grid (row, column, or diagonal of won boards; full-drawn boards never count) wins the game immediately.
6. If all nine local boards are closed and no player has a macro three-in-a-row, the game is a draw.
